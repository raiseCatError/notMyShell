## Owner corrections

- **Pause acknowledgement:** declining an approval and `/queue pause` share a pending intent. The request carries the reviewed queue revision where supported. The frontend retains the draft and withholds idle Enter routing until authoritative owner state arrives; acknowledgement never submits the draft. Success is announced only after an observed user pause. A changed revision/refusal or lifecycle change cancels the intent without assuming pause, approval or submission. Foreground program input retains priority. The dispatcher remains the only queue/execution owner.
- **Starting predecessor:** a manual submission can precede its exec marker. When a new chain joins that specific starting submission, its later observed exec is adopted into the chain. Its failure now holds the queue under the captured policy. Independent commands of an already-paused chain remain independent. No output or silence is treated as completion.
- **Interruption after resume:** Ctrl+C/exit 130 holds unpaused pending work even when the foreground command was independent of the chain. Plain failure attribution still requires chain membership; existing pause causes are preserved.
- **Task group lifecycle:** the supervisor no longer sends signals to saved numeric process-group IDs. A task-local Node guard starts in the PTY group, verifies that it is the group leader, then passes the exact original command as one `shell -c` argument. It signals group 0 from inside that group. A bounded, private control file retains the strongest stop request before readiness; a write records intent, never evidence of completed termination. The actual command leader's exit facts remain separate from the guard's eventual exit. Members that outlive that command leader remain reachable through the live guard. A deliberately detached process is outside the group. Shutdown waits for guard cleanup and fails if it cannot establish completion.
- **Guard startup isolation:** `NODE_*` and `TSX_*` settings are excluded from guard interpreter startup, then restored in the actual command child's environment. Values travel only in the spawn environment, never the task record, argv or a disk artifact. The initial group probe is bounded; leftover membership scans run at most every 250 ms. The guard kills its own group if its supervisor parent disappears.
- **Reviewed paste:** Block and Edit use the surviving reviewed entries in their displayed order after removal/reordering. Unmodified blocks keep their exact source; explicit original-text recovery remains available. Empty removed blocks cannot submit the original paste.
- **Summary privacy:** summary saving uses the existing scrollable, wrapped exact-text review. Compact/detailed display preferences cannot conceal persisted command arguments from inspection. Redacted command text is immutable during this save review; Enter/y confirms and Esc/n/Ctrl+C cancels. Automatic artifacts require affirmative owner-observed history eligibility before keeping recognized command labels; ignored, excluded or unknown eligibility uses a generic label. Both service and in-process owners propagate the same observation.
- **Teardown:** late queue snapshots are ignored after frontend stop, so they cannot restart presentation expiry. Canonical scratch and CI leak checks include the task guard lifecycle.

The task guard is an intentional architectural cost: one Node process per active task/group, a 25 ms control-file poll, and bounded process-table probes while members outlive the command leader. This avoids a [check-then-signal PID reuse window](https://man7.org/linux/man-pages/man2/pidfd_send_signal.2.html); an unknown membership probe retains the guard. No numeric-PGID fallback exists. This changes background-task supervision, not the persistent foreground ShellSession architecture.
