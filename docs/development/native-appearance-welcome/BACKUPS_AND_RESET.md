# Backups and guarded reset

Implements the supplied BRIEF-BACKUPS.md in the assigned worktree. No dependencies, PTY changes, shader generation changes, or release version changes.

## Design
A private, bounded journal records checked before-images and expected after hashes before the existing host transaction can mutate files. All readers reject symlinks and oversized files. Restores capture current snapshots for stale checking and create another journal entry, making undo reversible. Shared studio shells render history and a four-step reset state machine; no write occurs while planning or rendering. Reset discovers ownership and delegates to existing removal planners, retaining user content and reporting refused areas.

The shared transaction is preferred over independent backup implementations because existing snapshot checking and rollback remain authoritative. Legacy writers retain their own validation and use that transaction for their final write. State metadata needed to undo ownership changes belongs in the same journal entry as external files.

## Implementation details and safety decisions

`src/backups/journal.ts` stores private before-images and verified after-images. The expected after hash is present in a prepared manifest; a successful transaction verifies bytes and permissions and marks it applied. After-images let ownership-only reset reverse exact NMSh edits across saves while preserving user edits made between those saves. A restore is a new protected entry. It also checkpoints config.json without changing it unless settings were part of the chosen restore.

Entries publish by directory rename only after staged content and manifest read back correctly. Interrupted staging is retained for inspection and counts toward storage limits. A short exclusive process lock serializes entry creation; a lock from a demonstrably dead process can be recovered. Automatic, applied entries may be pruned. Reset, restore, manual and unfinished checkpoints remain protected. A private pruning index prevents legacy resets from treating an incomplete retained history as proof of original ownership.

Host appearance and shader removal use their existing planners. Legacy cursor, keyboard and Starship reset requires verified applied history with after-images, exact target paths, and unambiguous owned changed lines. Without that evidence, the area is skipped. Changed user lines are never guessed at. Theme Bridge and status-line writes checkpoint their ownership records in the same transaction as their host files; restoring an artifact therefore restores its ability to be managed later.

The reset wizard merges disjoint removal plans at whole-line boundaries. Conflicting plans are skipped with a reason. Every captured dependency is rechecked before and after the global reset checkpoint. Each area then uses the checked transaction and reports done, skipped or failed; remaining areas are skipped if an application fails. The global checkpoint remains available even after partial failure.

History uses the shared Studio layout; exact diffs, overwrite confirmation and scrollable result documents use the shared review renderer. Only optional control/subtitle parameters were added to that renderer. At small sizes the scroll position and cancellation/confirmation controls remain visible. Reset starts with no selection; settings are a separate area. A wrong final word cancels. No scheduler or animation loop was added.

Settings saves keep their merge-preserving behavior and take at most one daily checkpoint. Checked snapshots and exclusive staging prevent a save from overwriting a change that arrived during the backup. Host writes and reset/restore require HOME-contained, non-symlink paths. Legacy fixtures that intentionally write config now declare HOME and XDG consistently. Explicit NMSh state paths retain the settings API's existing state-directory behavior.

## Integrity follow-ups (D2–D4, 2026-10-29)

**Theme Bridge ownership record (D2).** Re-applying unchanged colors (every launch) no longer rewrites `theme-bridge/ledger.json`: an unchanged artifact keeps its `generatedAt`, and `commitLedger` writes nothing when the record already says the same thing. Every real record-only change (theme reference, include removal, bat cache) goes through the journal like any other configuration write; `saveLedger` is no longer used by NMSh itself. Restoring a backup that contains the record reconciles it per tool: a tool whose managed file or include this backup restores takes the backup's record for that part; every other tool keeps NMSh's current record (its files are untouched, so its ownership stays provable). The review lists each kept record, and the record is not reported as a "later user edit".

**Damaged targets (D3).** A journal entry is verified from its own files; the recorded target path is checked only lexically (absolute, inside HOME or NMSh's directory). Reading or writing a target still uses the full `checkPath` guard (no symbolic links, real directories, owner, permissions), and its errors now name the exact path and why. Consequences:
- a damaged target makes only that entry's restore fail, naming the entry, path and reason; nothing is written through it;
- `/changes` shows `unsafe: <reason>` for that file and keeps every other entry restorable;
- an entry whose own files fail verification is listed as unreadable with its reason, kept on disk, counted toward the limits and never pruned. Writes to a file that such an entry names are refused (fail closed for that file, with the folder to move aside); writes to other files continue;
- a manual snapshot skips unsafe paths and names them.

**Interrupted writes (D4).** `outcome` stays `prepared | applied` so older builds still read every entry; how an unfinished write ended is extra evidence in `resolution` (`reverted`, `rollback-incomplete`, `finalized`, `partial`). `Journal.transactionState` reconciles an entry from the bytes on disk, never from assumptions: `applied`, `in-progress` (another live process owns it), `not-applied`, `partially-applied`, `applied-unfinalized`, `conflicted` (a file now matches neither its before nor after image), `reverted`, `rollback-incomplete`, `partial`, `indeterminate` (a file cannot be read safely). An in-process failure records `reverted` or `rollback-incomplete`. In `/changes`, unfinished entries are counted in the notice and marked `!`; Enter reviews a rollback (a normal restore with its own undo checkpoint; only files whose bytes would change and differ from what NMSh wrote need the second confirmation), and `F` marks an entry applied only when every file holds the written bytes (no file is touched). A successful rollback marks the entry `reverted`, naming the undo checkpoint. Unresolved prepared entries are never pruned automatically. Tests kill a real writer process with SIGKILL after the entry is recorded, after the first of two files, and before finalization (`tests/backupsIntegrity.test.ts`).

Limits: the per-host appearance and shader ownership records each describe one file group and are always restored together with that group, so they are not reconciled per tool. PID reuse can make a long-dead writer look `in-progress`; that state blocks nothing but reconciliation advice.

## History, reset and retention (D5–D7, 2026-10-29)

**Readable history (D5).** Each row is `HH:MM <application> · <file> [+N more] · <created|changed|removed|checkpoint> · <status>`, grouped by local day. The application comes from the path (Kitty, Ghostty, Vim colors, Starship, NMSh settings, …); NMSh's own records (settings, ownership JSON) are never named as the subject when a user-facing file is in the entry. The writer's label stays visible as "Recorded as: <source> · <label>". Status distinguishes "changed later by NMSh (<time>)" (the file holds what a newer entry wrote) from "edited since" (something else changed it).

**One reset, one entry (D6).** A single-area reset is one transaction, so its own entry is the undo checkpoint (previously a separate checkpoint duplicated it). A multi-area reset keeps one "Reset checkpoint: A, B" of every file plus "Reset stage i/n: <area>" entries linked to it (`group`), because a later stage can start from a file an earlier stage changed. A failed stage marks the checkpoint `partial` with the per-area results. Navigation steps say what Enter does ("next: backup", "next: type reset", "restore now", "next: confirm overwrite"); only the typed word `reset` writes.

**Scoped settings reset (D7).** `config.json` has three reset areas: NMSh preferences, first-run state (onboarding, intro, tools setup, glyph style and choice) and update policy (`updateMode`, `updateFrequency`). Preferences never touch first-run state or the update policy; no scope touches the user's themes, `customTheme`, welcome presets, agent profiles, or fields this version does not know. Selected scopes are planned together as one exact change. The impact lists every changed setting as `key: before → after` and what is kept. A missing settings file is "nothing to reset"; malformed JSON is refused, never guessed at; a second reset is a no-op.

**Retention guarantees.** The journal keeps at most 200 entries / 64 MiB (unchanged). Never pruned automatically: unfinished entries (unresolved, or rollback-incomplete), the newest entry per source and file, and the 20 newest reset/restore/manual entries. Pruned oldest-first: every other entry, except each file's earliest kept backup ("original"); originals go only when nothing else can, oldest first, and each removal is recorded (path and time, newest 50) in `.pruned.json` and shown in `/changes` as a retention warning that suggests a manual snapshot. If even the never-pruned entries do not fit, the write is refused with that reason. So NMSh does not promise that the state before its first change is kept forever: it keeps it ahead of everything automatic and says when capacity pressure removed it. "Original" means the earliest backup the journal still has; files NMSh changed before the journal existed (builds before c3620236) have no pre-NMSh copy. A settings reset that keeps the update policy or first-run state writes out absent keys as their current effective value, so a legacy file cannot change meaning. Tested: 260 automatic writes to one file beside two edits of another keep both originals within 200 entries; a three-entry cap reports the original it removed.

Known cost: each journaled write lists and verifies the whole history (~0.4 s per write at 200 entries on this Mac); bursts of automatic shader writes pay it each time. Not changed here.
