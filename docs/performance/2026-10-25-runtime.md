## Findings and implementation

1. **Output bursts repeatedly build full transcript frames (CPU/rendering/allocations).** Deterministic production-frame test: 200 chunks caused 200 paints. Component profile: transcript presentation, wrapping and GC are substantial; unchanged 100k wrapping median 207.7 ms in a separate built-code harness. The implemented change parses every chunk synchronously but coalesces output-only paints within a 16 ms display tick. Keyboard, prompts and resize render immediately and consume pending output work; stop cancels its timer. Queries and raw passthrough are still synchronous. No output retention, input ownership, queue or paste policy changes; no cache, dependency or worker added.
2. **Whole transcript wrapping remains expensive (CPU/GC).** A line cache improved warm 100k wrapping to 99.3 ms but retained ~53 MB extra heap even after compacting strings, and resize worsened 175.0 → 245.5 ms. The earlier rope-string version retained ~148 MB extra. **Rejected and reverted.** Further work must avoid these memory/resize tradeoffs.
3. **Startup loads a large module graph (I/O/module compilation).** Separate profiled import: ~1,016 ms, ~103 MB RSS; CPU samples include module reads, linking/compilation and native addon loading. Profiled and cache conditions differ from the warm launch table: do not subtract these numbers. Optional Arcade/browser/document loading remains a high-priority investigation, not a proven implementation recommendation yet.
4. **Typing/history paths (CPU).** Existing component baseline: edit/layout/highlight median 7.54 ms (p95 10.04) for the generated long command; structured 100k-history query median 13.44 ms; repeated 100k suggestions median 3.10 ms. Grapheme segmentation and string-width work appear in profiles. These are useful next investigations, not measured gains from this PR.

## Verification and review

Independent read-only review identified two pointer/selection hazards introduced by delayed painting. Both are fixed: pending mouse events use a bounded snapshot of the last displayed viewport, and active selection dragging paints output synchronously so release cannot copy an unseen redraw. A second review approved the final implementation with no remaining concrete blocker. Regression tests cover these cases, Unicode wrap fragments, transcript clearing, burst ordering, immediate input, prompt/resize cancellation, capability queries, fullscreen handoff and shutdown. The full canonical `npm run verify` passed with two workers, a private short T7 test root, explicit TERM=xterm-256color / COLORTERM=truecolor and NO_COLOR unset. No tests were excluded or assertions changed. Known intermittent macOS read/input problems are not claimed fixed.

## Application profiling follow-up

Separate inspector CPU + 32 KiB allocation-sampling runs used the unchanged QA build at be3f6abe (matching lockfile) and the candidate, both with private config/service, the same command and explicit teardown. These runs are instrumented and are **not** the warm timing table. Frontend sampled allocations attributed to wrapStyledLine were ~240.25 MiB before / ~10.91 MiB after. Profiler totals include other startup/typing work and garbage-collected allocations; they are estimates, not retained-heap measurements. Frontend total user+system CPU was 1.328 s / 1.157 s in these single runs; cache conditions differed, so no causal whole-application CPU percentage is claimed. Profiled peak RSS was 297.22 / 298.73 MiB (essentially unchanged); event-loop p95 was 11.57 / 14.41 ms (worse in the candidate sample), maximum 120.72 / 96.01 ms. More runs are required before interpreting event-loop differences as regressions or gains.

The module-load hook recorded 121 Arcade modules even though Arcade was not opened (49–86 ms of instrumented load time, excluding subsequent compilation/linking). This establishes unused import overhead worth testing for deferral; it does not measure Arcade activation. Grapheme segmentation was a leading application CPU frame (~135–146 ms across these instrumented launch/type/output scenarios), motivating a separate input-layout slice.

The initial complete canonical run found two path-sensitive existing fixtures: textEditor’s full-path dialog text was truncated under a nested long T7 root, and tmpdirHygiene requires its runner root to be shorter than 32 characters. Both passed with the exact canonical environment and unchanged assertions under the short dedicated `/Volumes/T7Tmp/p25` root.
