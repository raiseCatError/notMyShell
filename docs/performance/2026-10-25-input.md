## Causes and changes

1. Each grapheme call constructed a native Intl.Segmenter, including calls for every editor token during cursor mapping. Actual application CPU profiles had already identified segmentation as a leading frame. Reuse one lazily created segmenter; each call still returns an independent array. Segmenter-only long-edit median: 201.97 → 54.40 ms. No input cache is retained.
2. Layout repeatedly measured the same ANSI prompt prefix for every glyph. Measure it once per row, updating only on row creation. Short-edit median after this stage: 1.07 ms; long-edit 48.96 ms. Narrow widths, wide glyphs and empty/styled prefixes preserve existing behavior.
3. Vertical movement recalculated the entire layout for every token boundary, also repeatedly calculating display offsets. Capture every caret position during one pass through the same wrapping implementation, then scan token boundaries once with the existing paste-label/Unicode mapping and earliest-index tie order. This avoids duplicated wrapping rules and quadratic work. Temporary caret storage is linear and released after movement.

A deterministic native-construction test failed on the original (20 calls constructed 20 segmenters). A navigation scaling test failed before the final change (doubling command length increased segmented characters 6,500 → 25,284). Both pass after the changes without timing ceilings. Compatibility coverage checks every token position for Unicode, separately inserted combining marks, wrapped paste labels, styled/empty prefixes and narrow widths. It caught an initial end-clamping omission for clusters joined across separate keystrokes; fixed to preserve original layout semantics.
